# Decisions

- Python 3.11 is the project baseline (`requires-python >=3.11`). The host exposes Python 3.13 only; no global runtime was changed.
- MSU-MFSD is blocked for record mapping until explicit official protocol/layout YAML is supplied.
- SiW-Mv2 inference records intentionally omit labels; the private adapter is evaluator-only.
- M2 defaults (4 uniform samples, 5% endpoint exclusion, 0.5 SCRFD threshold, 25% padding, 224px crops) are implementation defaults, not target-tuned values.
- SCRFD input is frozen at 320 under `scrfd_source_policy_v1`: source-only CASIA/MSU validation found equal valid-detection rates for 256 and 320, so the approved rule selects 320. Threshold remains 0.5.
- M3A packages preserve the exact M2 JPEG crop bytes instead of re-encoding to PNG. The spec snapshot suggested PNG, but the frozen M2 checkpoint produces validated JPEG artifacts whose SHA-256 identity is recorded in the M2 manifests; re-encoding would break that identity and apply a second lossy image transformation. Package rows therefore record `image_format="jpeg"` with the `.jpg` extension, and packaging verifies the copied bytes still match the M2 crop SHA-256.
- M3A contrast is reported as `contrast_michelson` rather than RMS contrast: for a single normalized grayscale crop, RMS contrast is numerically identical to `brightness_std`, so Michelson contrast is used to add independent information. The formula is documented in `configs/data/package_m3a.yaml`.
- M3A computes only detector-geometry and deterministic image-quality priors. Parsing masks, pose, visibility and identity embeddings require pretrained models and are recorded as `*_status="not_computed"`; no zero-filled placeholder arrays are written.
- M3B parsing and pose use the official FaceXFormer checkpoint (HF `kartiknarayan/facexformer`, revision `fd12148d0b19`, weight SHA-256 pinned). It depends only on torch/torchvision already present, so no separate environment was required and the 283-test environment was left intact. The 11 parsing classes follow the LaPa ordering, verified empirically from class centroids rather than assumed.
- M3B pose is recorded in radians (`yaw_pitch_roll_radians`) because the FaceXFormer head emits radian-scale values; the convention is pinned in the model registry and the package lock so no degree/radian mixing is possible.
- M3B visibility is derived from the parsing mask area per region, normalized by the detected face area, and attenuated for the cheeks by yaw-driven self-occlusion. It is never a constant vector, and a focused test asserts that yaw reduces the occluded cheek.
- M3B identity embeddings use the official AdaFace IR-50 WebFace4M release from the author's HuggingFace repo (`minchul/cvlface_adaface_ir50_webface4m`). Embeddings are computed only for source_train live samples; all other samples record `identity_status="not_applicable"` with no embedding array, so no identity signal can reach dev or target data.
- Third-party model code (FaceXFormer network, AdaFace net) is downloaded into the ignored model cache at load time rather than vendored into this repository, to avoid redistributing upstream code; the weights are verified against pinned SHA-256 values on every load.
- Package content identity excludes wall-clock and host-dependent lock fields (`created_at`, `build_seconds`, `git_commit`, `environment`). The first M3B resume rerun produced byte-identical manifests, shards and priors but a different `content_identity_sha256` because the promoted lock hashed `build_seconds`; excluding those fields makes the identity a function of package content alone, verified by two consecutive resume reruns.
- M4 encodes labels as `live=0`, `spoof=1`: spoof is the positive (attack) class, matching the presentation-attack-detection convention behind APCER/BPCER. The mapping is committed in `configs/data/loader_m4.yaml` rather than inferred from sorting.
- M4 uses separate `CanonicalSourceSample` and `CanonicalTargetSample` contracts instead of one dictionary with `None` placeholders, so a target sample structurally cannot carry a label, class target or identity embedding, and the collate paths are likewise split.
- M4 batches keep exact domain/class quotas (8 per pool at batch 32). Because source_train pools are imbalanced (casia live 160 / spoof 800, msu live 120 / spoof 360), one balanced epoch is not full unique coverage: minority pools are deterministically reshuffled and cycled. The audit therefore reports measured unique/reuse counts per pool rather than claiming each sample appears exactly once.
- M4 batch collation carries `identity_embedding [B,512]` with an `identity_available [B]` mask; zero rows are placeholders that are meaningless unless the mask is true, and target batches always report the mask as false.
- M5 B00 uses ConvNeXt V2 **Atto** (`convnextv2_atto.fcmae_ft_in1k`) from timm, which was installed for this milestone because torchvision ships only ConvNeXt V1. The registry was inspected before choosing, and the weight SHA-256 is pinned in the training config.
- M5 ran on **CPU**: this host's torch build is `2.13.0+cpu` with no CUDA device, so AMP was disabled and fp32 used. The device is recorded in run.json, environment.txt, the checkpoint and the report rather than assumed.
- B00 uses one loss, mean BCE with logits, with no class weighting, pos_weight, focal or label smoothing: the M4 sampler already balances every batch across domain and class, so re-weighting would double-correct.
- Checkpoint selection, temperature and threshold are all fitted on source_dev only. Target predictions are produced once under that frozen calibration, and target labels are never read, so M5 reports target score distributions but no target accuracy or FAS metrics.
- M6 remote package verification uses a shard-first `remote_parity` profile rather than re-running the exhaustive loose-file validator on Modal. Hashing and decoding 13,337 small files over a network-mounted Volume exceeded the container lifetime and was preempted twice; the 9 tar shards contain the exact jpg+npz+json payloads the remote trainer reads, so their SHA-256 values plus deterministically sampled real triplets are the authoritative remote transfer-integrity check. The full 59/59 local validator is unchanged and remains authoritative for the loose tree.
- M6 disables TF32 (`torch.backends.cuda.matmul.allow_tf32` and `cudnn.allow_tf32`) in the fp32 parity functions. Ada/Ampere GPUs enable TF32 by default, whose ~10-bit mantissa produced 1.03e-02 logit drift against CPU fp32. Parity is declared in fp32, so the numerics were corrected rather than the tolerance widened. The training smoke keeps AMP per the B00 device policy, where TF32 strictness does not apply.
- Modal jobs use the M4 shard loader by default; M4 already proved loose/shard sample equivalence, and streaming 9 tars avoids thousands of small-file opens on network storage.
- Model weights are loaded from the pinned volume file via timm's `pretrained_cfg_overlay`, so containers run fully offline (`HF_HUB_OFFLINE=1`) and can never silently fetch a different revision.
- M7 fixes `max_artifacts_per_recipe = 3`, `max_regions_per_recipe = 3` and `max_total_artifact_strength = 1.0` in `configs/recipes/ontology_m7.yaml`. These are **engineering safety defaults chosen to keep an operator graph bounded and a severity budget satisfiable**, not values tuned on source_dev or on any target data. No M7 number was selected by looking at detection performance.
- M7 compatibility rules (medium/artifact, geometry/region), safe strength bands, capture ranges, aliases and forbidden tokens all live in the ontology YAML rather than in Python conditionals, so a reviewer can audit the entire rule set in one file and the compiler cannot drift from it silently.
- The M7 bank is generated by an offline deterministic structured generator (`deterministic_local` / `deterministic-source-only-recipe-generator` / `m7-v1`), not by an LLM. The spec allows a frozen LLM provider, but depending on an API key or an unpinned hosted model would make the bank irreproducible, so `prompt.txt` is frozen as the contract a future pinned provider would receive and `generator.json` records `external_llm_invoked: false`. The compiler still accepts LLM-shaped JSON, including documented free-text aliases.
- M7 recipes are dataset-agnostic: the ontology's forbidden-token list rejects target identifiers, **and also the source dataset names**, dataset paths and machine paths. A recipe describes physics, so no dataset name has any business appearing in one.
- M7 canonical/left-right convention follows M3B: `left_eye`/`left_cheek` mean the **image-left** (viewer) side. This was re-verified empirically from LaPa class centroids on real source_train live priors (class 4 at x ≈ 0.35, class 5 at x ≈ 0.68) rather than assumed from the class names.
- M7 region masks are parsing-first with a documented geometry fallback because the frozen package genuinely lacks parsing classes on some samples: inner mouth (class 8) is present on only 25 of 80 sampled live priors and one eye can be missing under yaw. A parsing region under 24 px is treated as missing rather than used.
- M7 severity is enforced twice: the ontology's per-artifact safe band bounds what an operator was validated for, and the total-strength budget bounds the compound effect. A recipe outside either is rejected with a structured issue, never clipped silently.
- The M7 physics engine finalizes with `where(exact_edit_mask, transformed, original)` against the original tensor, so outside-mask preservation is proven **exactly zero**, not merely within a tolerance. A loose tolerance would have hidden operator support bugs that the exact composite makes impossible.
- M7 uses its own NumPy Gaussian/morphology kernels instead of OpenCV so mask and operator numerics cannot drift with a library version, and every random draw comes from a local `PCG64` generator seeded by `sha256(bank_id|recipe_id|recipe_seed|sample_id|operator_index)`; no global NumPy, Python or Torch RNG state is ever read or written.
- M7 diversity is audited with a locally computed TF-IDF cosine over deterministic recipe descriptions plus a structured conditioning-vector cosine. No text embedding model is downloaded, matching the offline, reproducible-bank constraint.
- M7 previews are audit artifacts, not synthetic training data: no quality score, no accept/reject manifest and no GPAT route exist yet. Those belong to M8, and claiming preview quality before the M8 gate has run would be unsupported.
- M8 saves its own artifact map for the physics route rather than reusing `PhysicsResult.artifact_strength_map`. That M7 field is a **preview** map — the per-pixel RGB difference divided by its own peak — so its masked mean measures contrast, not strength, and gating it against the recipe's requested strength is a units error: the correctness pilot measured 0.780 for a recipe requesting 0.0915 and rejected every physics candidate. M7's per-operator `strength_map` is already `support * strength`, and the GPAT artifact head is trained against `M_t * a_recipe` in those same units, so the M8 map averages the applied per-operator strengths over the graph and both routes are gated on one scale. M7 is not modified.
- M8 GPAT inference is fp32, batch-1 and cuDNN-deterministic (`benchmark=False`, `deterministic=True`). Batching can change kernel selection and therefore bytes, which would make a 32-candidate determinism rerun of a 1120-candidate bank meaningless; the residual model is 0.9 M parameters, so batch-1 costs nothing.
- The M8 artifact-map NPZ is written with an explicit `zipfile` member date of 1980-01-01 instead of `np.savez_compressed`, which stamps the local wall clock into every zip entry and would make byte-identical reruns impossible.
- M8 bank identity binds the **logical** manifest rows, not the parquet bytes, for the same reason as the M7 pair plan: pyarrow versions write different bytes for identical data. Parquet byte hashes are recorded as provenance outside the identity, alongside `created_at`, `bank_id` and the export archive.
- The M8 transport archive is excluded from BANK_LOCK identity by construction: it is one deterministic tar built only because a Windows directory download of thousands of small files failed in M6, and a bank must not change identity because of how it was moved.
- `BANK_LOCK.status` is derived from the operational-minimum result, never written as an unconditional `validated`. The first full 1120-candidate run missed two pre-declared minimums, and a hard-coded status would have made both the field and the validator's status check vacuous. A run that misses a minimum is retained and labelled `operational_minimums_failed`; it is never relabelled, and freezing under the immutable versioned path still requires a validated bank.
- The M8 source-isolation leak scan asserts the isolation evidence field by field instead of pattern-matching `target_test` in `generation_summary.json`. The required evidence is literally a set of keys named after the forbidden splits (`target_test_opened: false`), so a blanket token match flags the proof of isolation as a leak.
- M8 identity calibration is versioned rather than adjusted. v1 fitted `tau_id` as the 1st percentile of the identity cosine between an image and **the same image** under a ±2 % brightness/contrast nudge; that measures encoder sensitivity to a photometric change, not how an AdaFace embedding moves between two different observations of one person. v2 recalibrates from real `source_train` cross-observation pairs — genuine = same dataset, same identity, different `source_record_id`; impostor = same dataset, different identity — and freezes `tau_id_v2 = max(tau_genuine, tau_impostor)` by a rule declared before any candidate was re-evaluated. The v1 config, calibration, bank and archive are all left unmodified.
- M8 impostor pairs are same-dataset only and the identity key is dataset-prefixed. A CASIA/MSU pair differs in capture domain as well as identity, which would make the impostor problem artificially easy and depress `tau_impostor`; and CASIA subject 5 is not MSU subject 5, so the dataset prefix is part of the key rather than decoration.
- The M8 `max(tau_genuine, tau_impostor)` rule is a floor, not a choice: it holds the impostor false-match rate at or below 0.1 % even when the genuine distribution is loose. Measured on 560 genuine and 13440 impostor pairs the two distributions do not overlap at all (genuine min 0.5198 > impostor max 0.4812), so the rule is bound by the genuine population at `tau_id_v2 = 0.547440037939055`, with 98.93 % genuine acceptance and a 0.0 impostor false-match rate.
- A candidate's identity splits into a generation half and an evaluation half. Package, recipe bank, candidate plan, route binding, generator version and discrete convention determine the payload BYTES; calibration, threshold and fingerprint hashes determine only the DECISION. Re-calibrating the gate therefore reuses v1 payloads instead of regenerating them, and `discrete_from_saved` re-proves every discrete invariant from the saved bytes rather than trusting the run that wrote them.
- The M8 bank id prefix is versioned. The first v2 assembly produced `prism_synthetic_bank_m8_v1_…` for a bank built under a different calibration policy; a bank name that hides a policy change is misleading, so the prefix is now an explicit input and the validator resolves `calibration/quality_gate_v<n>.json`.
- Config loaders judge a config by what it opens, not by which words it contains. Both `load_quality_config` and the v2 loader previously rejected a config for honestly declaring `forbidden_splits: ["source_dev", "target_test"]`, and the bank leak scanner flagged `generation_summary.json` for containing the required `target_test_opened: false` isolation assertion. Declarations are now stripped at any depth before scanning, and the isolation evidence is asserted field by field.
- M8 structural calibration is versioned for the same reason identity calibration was, and this is the **final** planned revision. `tau_lm` and `tau_parse` were still the v1 values, fitted on the same-image ±2 % brightness/contrast population; that measures detector jitter under a near-identity photometric nudge, not stability under a non-geometric, identity-preserving *local* face appearance edit, which is what a synthetic candidate actually is. Under v2 the identity gate rejected 0 candidates while `landmark` rejected 467 and `parsing_dice` 233, and the implementation audit found no defect in coordinate transforms, mask semantics, the three preprocessing paths, discrete compositing, outside-mask equality, determinism or payload binding. v3 recalibrates from 280 `source_train` live images compared against **themselves** under 8 frozen appearance transforms inside one deterministic semantic region (2240 observations), and freezes `tau_lm_v3 = p99` of the same-image landmark NME and `tau_parse_v3 = p01` of the outside-support parsing Dice by rules declared in `docs/M8_STRUCTURAL_CALIBRATION_V3.md` before any candidate was re-evaluated. The v1 and v2 configs, calibrations, banks and archives are unmodified, and both superseded runs are retained with their `operational_minimums_failed` status intact.
- Cross-record genuine pairs are valid for **identity** calibration and forbidden for **structural** thresholds. Two different `source_record_id` values are two different observations and can differ in real pose, expression, head-geometry projection, landmark position, occlusion and crop; that is scene variation, not detector jitter caused by an appearance-only edit of one input. Measured, the 560 v2 genuine pairs give a landmark NME median of 0.0828 against 0.0013 for the same-image population, and their *1st percentile* alone is 3.3× larger than `tau_lm_v3` — so reading `tau_lm` off them would have licensed a candidate whose landmarks moved as much as a different photograph of the same person. They are computed and reported as a labelled diagnostic so the exclusion is evidenced rather than asserted, and a test enforces that no threshold derives from them.
- The v3 transform suite is fixed at 8 slots — brightness 0.90/1.10, contrast 0.90/1.10, gamma 0.90/1.10, Gaussian noise std 0.005, Gaussian blur sigma 0.75 — chosen and frozen before the run, and each transform is defined over the whole image before being restricted to the support so it stays a pure function of the image and its parameter. JPEG is excluded on the same grounds as v1 and v2: `cv2` JPEG encoding is not provably byte-deterministic across OpenCV builds. The blur is the only kernel in the suite and is a fixed symmetric low-pass filter that moves no coordinate; a focused test asserts a single bright pixel keeps its argmax position under every slot and that the blur stays symmetric about it.
- v3 scores parsing Dice outside the deterministic edit **support**, while the candidate gate scores it outside the **exact changed-pixel** mask. The gate's region additionally contains the in-support pixels that survived uint8 quantization unchanged, which agree by construction and can only raise a score, so the calibration sits on the conservative side of that difference. Rather than assume the gap is negligible, the outside-exact variant is computed and reported alongside as a labelled diagnostic: measured on the real 2240 observations it is p01 0.709456 against 0.709483 for the outside-support column, so the two agree to five decimals at the percentile that matters.
- A structural threshold fitted on a heavily censored population would not describe the population it claims to, so the v3 protocol refuses to report one unless at least 95 % of observations yield a valid landmark comparison, and it records detector failures separately instead of silently dropping observations whose NME would be large. The real run needed neither escape: 2240/2240 observations produced a valid comparison with 0 detection failures and 0 region-mask failures.
- The v3 determinism requirement separates metrics from thresholds. Per-observation metric values are compared within a tolerance of 1e-6 declared before the comparison, so a real device change is reported rather than silently absorbed; the derived thresholds, the threshold SHA and every logical identity must match **exactly**, and the tolerance is never widened after seeing a result. Both runs agreed with 0 mismatches.
- M8 declared in advance that v3 was the last calibration revision: if the v3 bank had still missed an operational minimum, the run would have been retained and the milestone reported as unable to meet its predeclared operational specification rather than recalibrated again. Changing the calibration population repeatedly until an acceptance count passes is threshold-fitting on the outcome, whatever it is called. The rule was written into `docs/M8_STRUCTURAL_CALIBRATION_V3.md` before the run, and it did not need to be invoked.
- M9 uses the local spec's architecture, losses, fusion, optimization and stage flow **verbatim** where `docs/spec_snapshot.md` fixes them, and marks everything else `SPEC_UNDERSPECIFIED` rather than presenting an invention as a requirement. Specified and therefore not chosen by this project: the nine-region set, the `F_local`/`T_global`/`RegionQuery`/`CrossAttention`/`RegionPool` decomposition, `d_r = min_k Mahalanobis`, `s_region = TopKMean(normalize(d_r), k=2)`, `s_final = 1-(1-p_global)(1-s_region)(1-p_prompt_spoof)`, all nine loss formulas and the `L_total` composition, `K_r=4`, diagonal covariance, batch 12/12/8, AdamW with backbone LR 1e-5 / head LR 1e-4 / weight decay 0.05, 5 % warm-up + cosine, 30 epochs after a 3-detector + 2-manifold warm-up, gradient clipping 1.0, AMP bf16-else-fp16, every lambda in Table 38, `margin_out=3.0`, and the `source_dev` ACER -> BPCER -> calibration-NLL checkpoint criterion. The full list of genuinely underspecified symbols and their defaults lives in `docs/M9_DETECTOR_CONTRACT.md` and `docs/M9_TRAINING_CONTRACT.md`, and every default sits in config rather than in code.
- `L_total` is implemented as written, which means `q` multiplies **only** the synthetic bracket — `L_cls_syn`, `lambda_local*L_local` and `lambda_out*L_out`. It does not scale `L_real`, `L_clean`, `L_MIL`, `L_prompt`, `L_cons` or `L_risk`, and it never touches `L_cls_real`. Reading `q` as a global sample weight would have been the intuitive guess and is not what the spec's formula says, so `L_cls` is split into an explicit real part and synthetic part instead. A focused test proves changing `q` moves the total while the synthetic label stays fixed.
- The local branch is ConvNeXt V2 **Atto**, not Tiny. Table 5 allows either ("ConvNeXt V2 Atto hoặc Tiny"), and Atto is already pinned, SHA-verified and uploaded to the models Volume by M5/M6, so choosing it adds no new unpinned dependency to a milestone that already introduces SigLIP2. The choice is a spec-permitted option, not a substitution.
- SigLIP2 Base P16-224 is **frozen** and only fusion/heads train on it, exactly as Table 5 states. The text encoder is likewise frozen and used once, offline, to embed the frozen M7 recipe descriptions into a cached constant matrix keyed by recipe id; §2.2 forbids fine-tuning the text encoder before a frozen-backbone ablation. At inference the fast path therefore needs no text encoder at all, only that cached matrix.
- PromptHead is built from the spec's two real statements about it — the signature in Table 32 and `L_prompt = InfoNCE(...)` in Table 35 — and **not** from M8's `recipe_match = not_applicable`. That M8 field is a quality-gate placeholder recorded precisely because no PromptHead existed at M8; reusing it as a training signal would fabricate supervision. PromptHead applies to synthetic samples only, on attacked regions with valid visibility, and contributes a masked finite zero for real live and real spoof.
- Regional losses and prototype updates exclude invalid-visibility regions **before** the normalization denominator is formed, rather than zero-filling them inside a mean. Zero-filling would silently shrink every regional loss in proportion to occlusion, making a heavily occluded batch look better optimized than it is. Each term divides by its count of applicable entries and returns a finite 0 when that count is 0, and each term is logged independently of the total so a legitimately zero term is visible rather than inferred.
- `clean_cap` defaults to `margin_out = 3.0`. The spec fixes the outlier margin but leaves the clean-region cap open; tying the two to one scale means a clean region is never pulled further toward its manifold than an attacked region is pushed away from it, which is the symmetry `L_out`/`L_clean` are built around. It is a config value, not a constant.
- M9 runs with **EMA disabled** and records `ema_enabled: false`. Table 37 makes EMA optional and explicitly requires reporting whether it was enabled; adding a second weight set whose effect is unmeasured would change what the reference checkpoint means. Enabling it is an M10 ablation.
- M9 executes spec stages **G1, G2, G5 and G6 only**. G7 (target prediction) and G8 (final scoring) are where target data first becomes readable, so they stay in M10 behind the controlled blind protocol. Table 62 sets M9's bar at "toy tests and source-dev training stable", which is why the `K in {2,4,6}` search, the B00–B08 baselines, the ablation matrix and the 3-seed statistics are all M10 rather than M9 — running them here would spend the target-free budget on comparisons M10 must own.
- The diagonal Mahalanobis distance is scaled as a **per-dimension mean**, not a raw sum over `D`. This is SPEC_UNDERSPECIFIED and was decided on measured evidence, not taste: the spec fixes neither `D` nor the scale convention of `d_r`, yet §10.4 pins `margin_out = 3.0` against that same `d_r` and `clean_cap` inherits it. A raw `D`-dimensional squared Mahalanobis has expectation `D` in-distribution, so at `D = 256` the very first real CPU batch measured `L_real` about 2.1e3 with `L_out` identically 0 and `L_clean` identically 3 — both declared constants were numerically inoperative and carried no gradient at all. Dividing by `D` gives `E[d] = 1` and places the spec's own `3.0` exactly where its numbers imply, at a 3x in-distribution deviation. Every formula, every margin and every declared loss weight is unchanged; only the one free scale is fixed. Both conventions remain selectable in config, and the choice enters the architecture identity so a checkpoint cannot silently change it. On the reference run the term became operative and non-degenerate (`L_out` about 4.6, `L_clean` about 4.6).
- G1 and G2 train on **real-only 16/16 batches**, not on the 12/12/8 mixed batch. Table 39 states G1's input as "Source real live/spoof" and only G5's as "Real + synthetic", so the synthetic quarter does not exist for the warm-up stages; dropping it and keeping Table 36's 1:1 real live/spoof ratio at batch size 32 gives 16/16. The split is SPEC_UNDERSPECIFIED and declared in `configs/train/m9_reference.yaml`. The manifold and synthetic loss terms are switched **off** in G1 rather than left to evaluate to a meaningless constant against absent prototypes, and the manifold terms come on at G2 once the prototypes exist.
- The frozen SigLIP2 vision tower is deliberately **excluded from the checkpoint** and bound by its verified SHA identity instead. It is 92,884,224 frozen parameters that never change; writing them into every checkpoint would add hundreds of megabytes per save and would let a `strict=True` load silently accept a different SigLIP2 build. The pin, re-hashed inside the container on every run, is both smaller and stricter than round-tripping the bytes.
- The recipe text cache is a **frozen uploaded artifact**, not a per-run recomputation. The first remote smoke proved the difference matters: encoding the 128 recipe descriptions with the frozen text tower is deterministic within one environment but not bit-identical across transformers 4.49 / torch 2.5.1 CUDA and transformers 5.14 / torch 2.13 CPU, so rebuilding it remotely produced a different content identity for identical science and the identity guard correctly refused the run. The cache is now minted once, uploaded beside the weights and only ever loaded and verified; rebuilding is opt-in and never used by a reference run.
- `run_id` is excluded from the config hash. It is a run **label**, and §11.1 makes changing it the consequence of a scientific change rather than the cause of one. While it was inside the hash, two runs of an identical configuration produced different prototype identities purely because of their names — which is exactly what the twice-run prototype determinism check exists to catch. The full resolved config still records the run id.
- The trainer seeds python, numpy and torch **before the model is built** and sets cuDNN deterministic. Without it the head, fusion and region-query weights came from ambient RNG state, so two independent prototype initializations of the same configuration disagreed. This was found by running the initialization twice, not by inspection.
- Target isolation is asserted **field by field and structurally**, never by scanning text for the word "target". The required evidence is literally a set of keys named after the forbidden things (`target_test_opened: false`), so a blanket scan flags the proof of isolation as a leak — the same mistake M8 already recorded. Dry-running the acceptance assembler reproduced it three ways: the isolation declarations, the frozen package lock's own `target_test` split count (provenance M9 copies without ever opening the split), and the report's own `not_claimed` disclaimer naming SiW-Mv2. The rule is now: a target-named declaration key must exist and be false, a target-named result key must be absent or null, a target-named number must be zero or the package lock's own split count, and the dataset name may not appear outside the narrative claim fields.
- A stage's completion marker on disk is authoritative over the lineage embedded in a checkpoint. A stage saves `last.pt` and only then writes `output_hashes.json`, so a checkpoint taken inside a stage records it as `RUNNING` even after it finished; a resumed run therefore reported a completed stage as still running. Resume now reconciles against the on-disk marker and records which stages it reconciled.
- The M9 reference run is **one scientific run**, `m9_reference_seed20260806`, even though two Modal invocations touched it. The first (`ap-4LRVozv73KDKe3XvQ68Dvy`) completed G1, G2 and G5 and then raised `TypeError: calibrate_source_dev() got an unexpected keyword argument 'config_hash'` in G6 — a demonstrated code defect in the container's pre-fix snapshot. The fix was already committed, so the same run id was resumed (`ap-kmwheVNBdohdIsncNiVifB`): G1/G2/G5 were reused from their locks and checkpoints, only G6 executed, and the resume began at global step 1575 rather than zero. A new run id is created when a scientific input identity changes, not when a process exits.
- M9 reports **source-side evidence only**. Table 62 sets M9's bar at "toy tests and source-dev training stable", and that is what the reference run demonstrates: 0 non-finite losses across all 1350 G5 steps, the exact declared composition in every batch, and monotonically improving `source_dev` NLL and ROC-AUC over 30 validations. `source_dev` was read only for checkpoint selection and the source calibration and produced no gradient. No SiW-Mv2, cross-domain, ablation or state-of-the-art claim is made anywhere; the experiment matrix and the controlled blind target evaluation are M10.
- M10's replication count is frozen by **declared scientific role**, not by assuming the spec's three seeds applies to every row. Section 20.1 requires "at least 3 seeds for main baseline and full method" and Table 58 requires "mean +/- std qua toi thieu 3 seeds"; Table 62's "3 seeds, baselines/ablations" is a milestone summary line, not a per-row rule, and the count for every auxiliary row is genuinely `SPEC_UNDERSPECIFIED`. Assuming 3 everywhere would exceed the compute budget and would have been quietly abandoned mid-matrix; assuming 1 everywhere would forfeit every statistical claim. So B00 and B08 carry 3 seeds because the spec names them; B06, B07 and the four ablations carrying H1/H3/H4/H5 carry 3 seeds because a declared hypothesis rides on them; every expensive diagnostic row carries 1 seed and is reported `single_seed_descriptive` with no interval and no superiority claim. The statistics module **refuses** a comparison whose either side is a single-seed row rather than silently attaching an interval to it. Seeds are `20260806/20260807/20260808`, frozen in `configs/experiments/m10_matrix.yaml` before any row was launched.

- The M10 firewall is a **resolvable-path permission check plus a capability object**, never a string scan, and this is now the third milestone to record the same lesson: the required evidence of isolation is literally a set of keys named after the forbidden things (`target_labels_opened: false`), so a blanket token match flags the proof of isolation as a leak. Declaration subtrees are skipped structurally by the config scanner; paths are compared after `Path.resolve()` so `..`, a symlink or a relative spelling cannot slip past; and G8's absence of a training capability is proved by an AST audit of its own imports and of its module-level import closure, distinguishing module-level imports (which are capabilities) from function-local ones (which are not).
- G8's model-state write rule is checked **before** the root permission rule. Both refuse, but checking the root first hid the stronger reason behind a weaker one - a `best.pt` aimed at the prediction root reported "may not write prediction_root" rather than "may never write model state", and the model-state rule must apply to every destination, including a path outside every declared root.
- ACER and HTER are the same functional and are kept as separate reported metrics because their **threshold source** differs: ACER at the frozen source-dev operating threshold M10 must actually deploy, HTER at the target EER threshold, which is the conventional cross-domain reporting point. Both sources are recorded beside the value so the two can never be read as independent evidence.
- The unknown/reject threshold is declared `not_fitted` with `unknown_threshold: null` rather than invented. Spec section 16.2 requires it to come from source-dev corruption/synthetic unknown exposure and forbids a target quantile; that fit (G6b) has not been performed, so nothing is rejected, the rejection rate is 0 by construction rather than by measurement, and every reject-dependent metric reports `not_applicable` with that reason. Risk-coverage needs only a confidence ordering and is still computed.
- Open-set/unknown AUROC/AUPR is declared `not_applicable` on this protocol: SiW-Mv2 provides no unknown-class label, and deriving one from the attack families would be fabricating a label. A metric that cannot be computed is reported as a status and a specific reason, never as `0.0` or `null`, so a reader can tell "we could not" from "we measured zero".
- A target prediction writes `null` for an evidence term the variant does not have, never `0.0`. A fabricated zero would enter the Table 34 fusion arithmetic and the report as a measured value; `null` cannot. `s_final` for such a variant is the same formula with fewer factors - `1 - (1 - p_global)` collapses to `p_global` - not a second formula.
- **`p_prompt` is a structural zero on target data, for B08 as well**, and is therefore written as `not_applicable`. Found by the label-free G7 smoke, not by inspection: `PromptHead.applicability` is `is_synthetic AND attacked-region AND visible`, and a target sample is never synthetic and carries no attack-region mask, so the head returns an exact 0 by construction. G7 now reads the model's own `prompt_applicable` mask rather than a config flag. The fused score is unchanged - `1 - (1 - 0)` is the identity factor - so the prediction logical identity was byte-for-byte the same before and after the fix, which is the proof that only the honesty of the column changed. Two consequences are recorded in the target evaluation contract: on target data B08's fusion reduces to `s_final = 1 - (1 - p_global)(1 - s_region)`, and the A08 prompt ablation can only differ on target through **training** - `L_prompt` shaping the shared region embeddings - never through inference-time fusion.
- `frame_id` in a target prediction is the deterministic ordinal of the frame within its video in frozen `sample_id` order, not the real in-video frame index. The frozen package manifest does not carry that index: M3A/M3B keep only the opaque `sample_id`, which hashes it without exposing it. Recovering the real index would mean re-opening the raw video tree, which G7 has no permission to touch. It is an ordering key for the aggregation join and is never read as a timestamp.
- A prediction produced for engineering verification is labelled `engineering_smoke: true` / `scientific_use: false` in its own lock. G8 refuses to score it as a scientific result and the lockset builder refuses to admit it, so a plumbing check can never be quietly counted as an experiment.
- The paired bootstrap seed is derived **structurally** from the comparison - `sha256(schema | seed | resamples | statistic | sha256(sorted video ids))` - rather than from the raw integer, so the same comparison always draws the same videos and a different comparison cannot accidentally reuse a plan. The resulting index matrix carries its own `bootstrap_plan_identity`, which is what proves determinism rather than a promise of it. Seed variability (mean +/- std over 3 seeds) and evaluation-set variability (the video bootstrap) are reported as separate axes and never combined into one interval, because they answer different questions.
